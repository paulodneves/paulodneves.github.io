Guia de Domínio · Event Sourcing

Estado é derivado.
Evento é a verdade.

Do zero ao domínio do padrão arquitetural que transforma como você persiste, audita e entende seus dados — para sempre.

4 fases de domínio
5 pilares essenciais
1 princípio que muda tudo
Fase 0 · Ponto de Arquimedes

A Peça de Dominó

O único conceito que, ao cair, derruba todas as outras dificuldades do tema.

CRUD

Estado sem História

-- ❌ Você só sabe ONDE está.
-- Não sabe COMO chegou aqui.

UPDATE accounts
  SET balance = 1000
  WHERE id = 'acc-123'

-- Depois disso: silêncio.
-- O passado desapareceu.

Você armazena o onde está. Perdeu para sempre o como chegou.

versus
Event Sourcing

A Fita Completa

-- ✓ Cada fato gravado para sempre.

AccountOpened   { balance: 0 }   # t=0
MoneyDeposited  { amount: 500 }  # t=1
MoneyWithdrawn  { amount: 200 }  # t=2
MoneyDeposited  { amount: 700 }  # t=3

-- 0 + 500 − 200 + 700 = 1000 ✓

Você armazena o que aconteceu. O estado emerge do replay.

⊕

A analogia perfeita: O Event Store é a contabilidade por partidas dobradas — o sistema financeiro mais confiável jamais inventado. Um banco não armazena "saldo atual" e descarta os lançamentos. Ele guarda cada transação. O saldo é apenas a soma. Event Sourcing é a contabilidade das suas aplicações.

Fase 1 · Fundamentos de Ferro

Os 5 Pilares

Os 20% de conceitos que geram 80% da compreensão prática.

01 · Pilar

Event

fato imutável que algo aconteceu

Sempre no passado: PedidoColocado, nunca CriarPedido. Uma vez gravado, não existe update, não existe delete. É o que aconteceu — atômico, imutável, verdadeiro.

Schema mínimo
eventId · aggregateId · eventType
timestamp · version · payload
02 · Pilar

Event Store

o ledger sagrado, append-only

Log append-only. A única fonte de verdade do sistema. Eventos organizados em streams — um por instância de aggregate. EventStoreDB, PostgreSQL com constraint, ou Kafka. O critério: nunca modifica, só acrescenta.

Invariante absoluta
INSERT only · no UPDATE · no DELETE · forever
03 · Pilar

Aggregate

o ator do domínio

Recebe commands → valida regras de negócio → emite eventos → reconstrói estado via replay. O estado do aggregate nunca é persistido diretamente. Para carregá-lo: fetch stream → replay → estado emerge.

Ciclo de vida
Command → Validate → Emit Event → Apply State → Persist Stream
04 · Pilar

Projection

read model / lente de consulta

O Event Store é péssimo para queries — é um log, não um banco relacional. A Projection consome eventos e constrói views desnormalizadas. Você pode ter N projections dos mesmos eventos. É aqui que entra o CQRS.

Regra de ouro
1 Event Store → N Projections independentes
05 · Pilar · O Superpoder

Event Replay

time travel · auditoria perfeita · projeções regeneráveis

A qualquer momento, você reconstitui qualquer estado em qualquer ponto no tempo. Bug na Projection por 3 meses? Delete, corrija o código, replaye todos os eventos — Projection limpa, como se o bug nunca tivesse existido. "Qual era o estado do pedido dia 15/11 às 15h?" — replay até aquele timestamp. Nenhum outro padrão de persistência oferece isso.

Casos de uso exclusivos
Time travel · Projection rebuild · Audit trail automático · What-if scenarios · Debug de produção sem logs
Fase 2 · Consolidação e Alavancagem

As Autópsias

Um sucesso retumbante e um fracasso catastrófico — o mesmo padrão, contextos opostos.

Sucesso

Kafka + LinkedIn

Martin Kleppmann e a equipe do LinkedIn precisavam rastrear todas as atividades dos usuários e alimentar múltiplos sistemas downstream — recomendações, analytics, feed — sem perder dados.

  • Cada ação do usuário → evento gravado no stream
  • N Projections independentes consumindo os mesmos eventos
  • Kafka como event store distribuído de alta escala
  • Greg Young formalizou o padrão criando EventStoreDB
  • Adotado por Netflix, Uber, Airbnb e centenas de empresas
Fracasso

Event Sourcing em Cadastro de Usuários

Uma startup aplicou Event Sourcing no cadastro simples de usuários (nome, email, telefone). Seis meses depois, o colapso:

  • Cada update de perfil: 3–5 eventos gerados
  • Carregar um perfil simples: 400 eventos de replay
  • Listagem com 50 usuários: 20.000 eventos processados
  • Time debugando "qual era o nome antes do email de 3 semanas atrás"
  • Informação que nunca importou para o negócio
Regra de Ouro

Se a pergunta "o que mudou neste registro e quando?" nunca vai ser feita pelo negócio, você não precisa de Event Sourcing. ES resolve domínios ricos onde o histórico importa: finanças, pedidos, logística, saúde, compliance. Para cadastros simples, é engenharia de over-design pura.

Fase 3 · Masterização

O que o 1% Sabe

Detalhes que 99% ignora — mas que definem o arquiteto de elite.

01 · Performance
Snapshots
otimização de replay

Conforme o aggregate acumula eventos, o replay fica custoso. Um pedido com 1.000 eventos leva 1.000 iterações. Solução: snapshot periódico do estado atual a cada N eventos. Próxima leitura: snapshot@900 + replay(901..1000) em vez de replay(1..1000).

snapshot(estado atual) → armazenar → próximo load: snapshot + apenas eventos recentes
02 · Evolução
Event Versioning
o problema silencioso

Você lançou OrderPlaced { items } em v1. Em v1.5 adicionou shippingAddress. O Event Store tem eventos de ambas as versões. Estratégias: Upcasting (transforme na leitura), Weak Schema (campos opcionais), Versionamento explícito (OrderPlacedV1, OrderPlacedV2). Regra absoluta: um evento gravado é imutável para sempre.

Você não migra eventos. Você os transforma na leitura via Upcaster.
03 · Distribuição
Sagas
coordenação multi-aggregate

"Processar um pedido" cruza: Order + Payment + Inventory + Shipping — aggregates distintos, transações distribuídas impossíveis. Uma Saga é um coordenador stateful que escuta eventos de múltiplos streams, emite commands para os participantes, e gerencia compensações. Não existe rollback de banco — existe um CompensatingEvent que semanticamente desfaz o anterior.

Saga escuta → emite commands → compensa via novos eventos. Nunca deleta. Sempre acrescenta.
04 · Tradeoff
Eventual Consistency
a escolha arquitetural

Com projections assíncronas existe uma janela onde o Event Store está atualizado mas a Projection não. Usuário faz pedido → OrderPlaced no Event Store → Projection ainda processando → listagem não mostra o pedido. Isso não é bug — é escolha deliberada. O 1% projeta a UX para isso: spinners, mensagens de confirmação, WebSocket push quando a projection atualizar.

Eventual consistency não é bug. É o preço da escalabilidade de projections independentes.
05 · Confusão Fatal
ES ≠ EDA
dimensões ortogonais

Event-Driven Architecture (EDA) é um estilo de integração entre componentes via eventos. Event Sourcing (ES) é um padrão de persistência onde estado = replay de eventos. Você pode ter EDA sem ES (Kafka para comunicação, banco relacional para persistência). Pode ter ES sem EDA (aggregate local, sem broker). São dimensões ortogonais. Confundir os dois revela gap conceitual imediato em qualquer entrevista sênior.

EDA = como os componentes se comunicam · ES = como o estado é persistido. Independentes.

Glossário de Autoridade

// termos que definem o vocabulário do 1%

Command

Intenção de mudar estado. ColocarPedido. Pode ser rejeitado pelo aggregate se regras de negócio falharem.

Event

Fato que já aconteceu. PedidoColocado. Imutável. Passado. Eterno. Nunca rejeitado — já ocorreu.

Stream

Sequência ordenada de eventos pertencentes a um aggregate específico. Um stream por instância de aggregate.

Idempotência

Capacidade de processar o mesmo evento N vezes sem efeito colateral. Essencial para projections resilientes a redeliveries.

Upcasting

Transformação de eventos de versão antiga para versão nova no momento da leitura, sem alterar o Event Store.

Process Manager

Coordenador stateful de fluxos de negócio que cruzam múltiplos aggregates. Sinônimo: Saga.

Compensating Event

Evento que semanticamente "desfaz" um evento anterior. Não deleta — acrescenta. O registro histórico é preservado.

Outbox Pattern

Técnica para garantir publicação exactly-once mesmo com falhas entre escrita no DB e publicação no broker de mensagens.

CQRS

Command Query Responsibility Segregation. Write side: aggregates + event store. Read side: projections otimizadas por query pattern.
